## 1. 목표와 비목표

**목표**

## 5. 사람 판정 설계 (ADR-0003)
- 100개 = 판정자별 단독 40 + 공통 20(사용자·팀원). 간극 세션과 대조군을 고유 순서 단위로 층화 추출, 한 고유 순서는 한 번만. 후보 생성에 쓴 세션과 동일 IP·동일 캠페인 묶음은 한 판정자 몫으로 몰리지 않게 분산한다. 순서별 세션 수는 가중치로 기록.
- 범주(초안, 판정 전 동결): ① 셸 진입만 ② 장비·환경 정찰 ③ 도구/파일 반입 시도 ④ 지속성·정리 시도 ⑤ 기타·판정 불가. 입력 문자열 관찰만, 성공·악성 판정 없음.
- 도구: CSV 시트(세션 ID, 방어 처리한 입력 원문, 판정 칸, 메모). 규칙·군집·후보 정보 숨김. 공통 20개는 두 시트에 순서를 다르게 섞음.
- 일치도: 공통 20개로 Cohen's κ·일치율·혼동 행렬. 표본이 작아 κ 신뢰구간이 넓다는 점을 함께 표기. κ가 낮으면 범주표를 새 버전으로 고쳐 다시 판정.
- 판정 시기는 팀원과 협의 후 확정. 그 전까지 E2는 보류한다.

## 6. 폐루프 최소 기능 (T7a, 제품 가치 유지)
자동 반영 없음. 관리자 승인과 검증이 필수다.

```
미식별 행동 발견 → 후보 생성 → 근거·관련 세션 제공 → 관리자 승인/거부 → 승인 규칙 반영(버전 관리) → 반영 전후 성능 비교
```
- **후보 저장소**: 후보(ID, 정규식, 생성 방식(A~D), 근거 세션 ID, IP 수·활동일, 상태 `proposed/approved/rejected`, 승인자·시각·사유)를 파일로 기록한다. 원본 IP·공격자 입력 원문은 저장소에 두지 않는다(세션 ID와 방어 처리한 요약만). 저장 위치는 git 제외 폴더.
- **관련 세션 제공**: 후보별로 일치 세션 목록(마스킹된 IP, 시각, 방어 처리한 입력 요약)과 전체·증분 일치 수.
- **승인/거부**: CLI(`approve`/`reject`, 사유 필수). 승인되지 않은 후보는 반영할 수 없다.
- **반영과 버전 관리**: 승인된 후보로 **새 규칙 파일 버전**(예: `signatures/versions/rules_vNNN.yaml` + 변경 요약, 이전 해시)을 만든다. `rules.yaml` 자체는 사용자의 명시적 요청이 있을 때만 교체하고, 커밋은 별도로 한다. 모든 반영은 이전 규칙 해시와 새 규칙 해시를 기록한다.
- **반영 전후 비교**: 같은 데이터에 이전·새 규칙을 적용해 커버리지, 구체화율, 회귀(잃은 적중) 0건 여부, 새 규칙 일치 수·증분을 보고서로 만든다(기존 `evaluate_coverage.py --baseline-rules` 방식 참고).
- UI(T7b)는 이 기능의 읽기 전용 화면으로 후순위다. 최소 기능은 CLI로 충족한다.

## 9. 위험
1. 현재 데이터에서 후보가 적고 소수 IP 반복이라 극적 개선이 안 나올 수 있다. 그 경우 한계와 방법론이 결과다.
2. B·D가 비슷하게 나올 가능성이 높다.
3. E1 대상 규칙이 9개라 통계적 힘이 약하다. 신뢰구간으로 보고.
4. 개발 검증 구간의 독립성이 없어 최종 평가는 F 이후 데이터에 의존한다. 데이터가 적으면 파일럿에 그친다.
5. 사람 판정 일정은 팀원에 달려 있다.
6. T0 실패 시 D팔의 공정 비교가 불가능하다(팀원과 협의 필요).
7. 일정이 빠듯하다.
