## 3. Slack 알림 설계 (설계만, 구현 안 함)

### 목적
운영자가 대시보드를 매일 열지 않아도 **중요한 변화만** 받는다. 알림이 많으면 아무도 보지 않으므로 종류를 적게 시작한다.

### 알림 종류 (1차 범위는 A·B만)

| 코드 | 언제 | 근거가 되는 기존 계산 |
|---|---|---|
| **A. 아침 요약** (하루 1회) | 정해진 시각마다 | `intel.briefing`의 세션 수·변화율, 새 IP·새 규칙, 위험도 높음 세션 수 |
| **B. 위험 등급 알림** (즉시) | 상황 등급이 **안정/주의 → 위험**이 될 때 | `intel.threat_level`: 새 다운로드 서버, 내려받아 실행(S01·S02), 새 파일 해시 중 하나라도 |
| C. 새 규칙·새 패턴 (후순위) | 이전에 안 걸리던 규칙이 처음 걸릴 때 / 규칙에 안 걸리는 새 군집이 생길 때 | `briefing`의 `new_rules`, ML `novel_candidates` |

### 메시지에 넣을 것 / 넣지 않을 것
- 넣을 것: 등급과 이유(예: "새 다운로드 서버 2개, 내려받아 실행 3세션"), 기간, 건수, 대시보드 링크.
- **넣지 않을 것 (원칙 7절 준수)**
  - 전체 IP 목록: Slack은 외부 서비스다. 기본은 건수와 마스킹한 IP(`a.b.x.x`)까지만 보내고, 전체 IP는 대시보드 링크로 확인하게 한다. 전체 IP를 보내려면 팀 승인이 필요하다.
  - 공격자 입력 원문: 보낸다면 `hxxp://`로 바꾼 URL 등 무해화한 형태만.
  - "공격 성공"이라는 단정: 탐지는 입력 관측이다. 문구는 "관측됨"으로 쓴다.
- Webhook 주소는 비밀 정보다. 코드·저장소에 넣지 않고 환경변수(예: `HONEYPOT_SLACK_WEBHOOK`)로만 받는다.

### 중복 방지
- 어떤 알림을 이미 보냈는지 기억해야 한다. 알림 기록 파일(예: 데이터 폴더 안 `alerts_sent.json`)에 `(알림 종류, 기준 항목)`을 저장한다.
  - B: 등급이 올라간 시점에 한 번. 같은 사유(같은 서버·해시)는 다시 보내지 않는다.
  - A: 날짜당 1건.
- 기록 파일이 없거나 깨져도 안전하게 동작해야 한다 (최악의 경우 한 번 더 보내는 정도).

### 실행 방식
- 데이터가 갱신될 때마다 알림 스크립트를 실행한다. 서버가 없는 지금은 **수동 갱신 → 스크립트 실행** 순서.
- 서버가 생기면 갱신 직후 자동 실행(cron/작업 스케줄러)으로 연결한다.
- `--dry-run`: Slack으로 보내지 않고 보낼 메시지를 터미널에 출력. 처음 쓸 때와 테스트에서 사용.

### 구현 전에 확인할 것
1. `intel.briefing`/`threat_level`이 Streamlit 없이 호출 가능한지 (현재 `streamlit_app/intel.py`에 있고 `ds`(데이터 객체)를 받는다). 불가능하면 알림 스크립트용 얇은 진입점이 필요하다.
2. 기준 기간: 아침 요약은 "어제 하루"인지 "최근 7일 비교"인지 정한다. 현재 `briefing`은 전체 기간 선택 시 최근 7일을 쓴다.
3. 메시지에 전체 IP를 넣을지 (위 원칙: 기본 마스킹).
4. 테스트: 합성 데이터로 `--dry-run` 출력과 중복 방지를 검증한다 (실제 Slack 전송은 테스트하지 않는다).
