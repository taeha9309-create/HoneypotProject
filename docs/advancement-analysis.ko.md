### 판정 (근거 포함)
- **군집 2: 단순 군집, 보완 불필요.** 구분되는 행동이 아니라 "셸만 연 접속"이다. 대표 순서가 100%이고 다른 정보가 없다.
- **군집 4: 규칙 보완 후보(B19 세분화).** B19 하위로 "IoT 텔넷 메뉴 순회"를 구분할 수 있다. 같은 대상을 `work/rule_candidates/FREEZE_X04.md`가 이미 후보로 다뤘고 승격은 보류됐다. 이번 측정에서 군집 4가 그 순서와 일치함을 재확인했다.
- **군집 5·7: 규칙 보완 후보(새 탐침 규칙).** `busybox <토큰>` 탐침은 데이터 전체에서 `echo`(13,935), `HISILICON`(9,658), `UNSTABLE`(472), `HolyFuck`(78), `CM35goCW`(21), `OWARI`(11) 등 여러 토큰으로 나타난다. 토큰마다 별개 규칙을 쓰면 변종이 빠져나가므로 "busybox 뒤의 임의 토큰" 형태로 일반화하는 규칙이 후보다. 이 토큰들이 알려진 봇넷 계열과 같은지는 **이 데이터만으로 알 수 없고 외부 자료 확인이 필요하다(미확인).**
- **군집화 오류는 아니다.** 군집 경계(메뉴 순서가 있는가, 마지막 탐침이 있는가)는 실제 명령 차이와 일치한다.

### 중요한 비판
- 이 네 군집에서 **군집화는 같은 순서를 모아 준 것 이상의 정보를 주지 않는다.** 고유 순서가 1~2개라서 "정확히 같은 순서끼리 묶기"만 해도 같은 결과가 나온다. 군집의 가치는 순서가 약간씩 다른 변종을 한 묶음으로 보는 데 있는데, 이 데이터에는 그런 변종이 거의 없다(변종 후보 약 25세션). 따라서 "군집이 단순 그룹핑보다 낫다"는 주장은 **이 데이터로는 아직 뒷받침되지 않는다.** 비군집 비교군(고유 순서 그룹핑)이 군집 기반과 비슷하게 나올 가능성이 높고, 그 경우도 정직하게 보고해야 한다.
- 이 1,259세션은 IP 9개에서 왔다. 소수 봇이 반복한 것이라 일반화 근거로는 약하다.

## 3. `cluster.py` 이상 점수 문제 분석 (읽기 전용, 코드 수정 없음)

- 판정 코드: 프로토콜 전체 이상 점수의 95분위수를 임계값으로 쓰고 `점수 > 0 이고 점수 ≥ 임계값`이면 "outlier"로 표시한다(`ml/cluster.py`의 `OUTLIER_QUANTILE`).
- 실측(현재 데이터): 텔넷에서 **점수가 정확히 0인 세션이 50.6%**이고 95분위수는 0.00002다. 그래서 점수가 사실상 0인 세션 761개가 outlier로 잡힌다. 점수가 0.05 이상인 세션은 122개뿐이다. SSH는 표본이 86개로 달라서(95분위수 0.989) 이 문제가 거의 없다.
- 원인: 같은 순서를 반복하는 봇이 점수 분포의 절반을 0에 몰아서, 분위수 기준이 사실상 "0보다 조금이라도 크면"으로 무너진다.
- 개선안(제안만, 팀원 협의 필요): (1) 절대 하한(예: 0.05) 병행, (2) 고유 순서 단위로 점수를 계산한 뒤 분위수 적용, (3) 군집 단위 기준. 현재 대시보드는 `NOVEL_MIN_OUTLIER = 0.05`로 화면에서만 보정한다.

## 4. 기준선 측정 방법 설계

목표: 같은 데이터·같은 규칙 해시에서 개선 전후를 비교할 수 있는 재현 가능한 측정.

1. **입력 고정**: 데이터 스냅샷 해시, `rules.yaml` sha, `NORMALIZE_VERSION`, ML 파라미터를 실행 기록에 남긴다. 동결 파일은 수정하지 않는다.
2. **단위**: 모든 지표를 (a) 세션 단위, (b) 고유 순서 단위, (c) IP 단위로 계산한다. 주 보고는 (b)와 (c)다.
3. **분할**: 시간 분할(11/18 이전 후보 생성, 이후 평가)과 IP 분할(평가 IP는 후보 생성에 쓰지 않음). 두 허니팟을 서로의 홀드아웃으로 쓰는 분할도 한다(서울로 만들고 시드니에서 평가).
4. **지표 계층**: 커버리지(참고) → 구체화율 → 규칙 제거 실험 재현율·정밀도·F1(숨긴 규칙의 적중이 정답, 한계 명시) → 사람 판정 정밀도.
5. **산출**: `ml/analysis/`에 읽기 전용 측정 스크립트, 결과는 `work/`(git 제외)와 요약 표는 문서에 기록.

### 비교 실험 (연구 질문 3)
- 기준: 현재 규칙 29개
- 비군집 개선: 고유 순서 그룹핑, 첫 명령 기준, 명령 수·편집 거리 기반 묶음에서 만든 후보

- 같은 입력·같은 후보 생성 절차·같은 분할로 비교한다. 후보 승인은 사람이 하되 승인 기준은 사전 동결한다.

## 5. 사람 판정 표본 설계 (ADR-0003)

- **표본 추출**: 규칙 간극 세션(미적중 + B19-only)과 대조군(구체 규칙에 적중한 세션)을 고유 순서 단위로 층화 추출한다. 처음 100개, 필요하면 200개 이상. 한 고유 순서는 한 번만 뽑고, 순서별 세션 수는 가중치로 따로 기록한다.
- **라벨링 기준**: 입력 문자열에서 관찰 가능한 행동 범주만 쓴다(예: 셸 진입만, 장비 정찰, 파일 반입 시도, 지속성 설치 시도, 기타/판정 불가). 성공 여부나 악성 판정은 하지 않는다. 범주표는 판정 전에 동결한다.
- **도구**: 처음에는 CSV(세션 ID, 입력 원문(방어 처리), 후보 규칙 일치 여부 숨김, 판정 칸)로 충분하다. 규칙·군집 결과는 숨기고 판정해서 앵커링을 줄인다. 두 사람이 겹치는 30개를 판정하면 일치도(Cohen's κ)를 낼 수 있다.
- **누출 방지**: 후보를 만들 때 본 세션은 평가 표본에서 제외한다. 규칙 정규식을 평가 결과를 보고 고치지 않는다(고치려면 새 ID로 다시 동결). 정답 라벨 없이 군집 번호를 정답처럼 쓰지 않는다.
- **구분**: "시그니처 매칭률(커버리지)"과 "탐지 성능(사람 판정 기준 정밀도·재현율)"을 표와 문장에서 분리해 표기한다.

## 6. 사용자 가치: 가상 시나리오 (전부 가설, 검증 전)

주 사용자: 전담 보안 인력이 없는 중소기업 IT 관리자. 보조: 연구자.

> **시나리오 A, 월요일 아침 5분 점검 (가설)**: IT 관리자가 대시보드를 열어 "이번 주 새로 보인 행동 N개, 이미 아는 행동의 변종 M개"를 본다. 변종과 새 행동마다 "우리 서버에서 확인할 것"(예: 외부에 열린 텔넷 포트, 기본 계정)을 본다.
> **시나리오 B, 차단 목록 (가설)**: 내려받기 시도에 쓰인 서버·IP·해시를 방화벽에 넣을 목록으로 받는다. 오탐 시 정상 IP를 막으므로 검토 후 반영한다.
> **시나리오 C, 규칙 검토 (연구자·운영자)**: 규칙 후보와 근거 세션을 보고 승인·보류·무시하고, 승인하면 전후 구체화율을 본다.

검증 상태: **인터뷰 불가 미확정.** 지인 중 IT 관리 경험자 2~3명에게 시나리오 A를 보여 주고 "무엇이 쓸모없는가"를 묻는 것이 최소 검증이다. 그 전에는 "도움이 된다"고 주장하지 않는다.

### 현실적 위험
1. 현재 데이터에서 발견 가능한 새 후보가 적다(변종 후보 약 25세션, B19-only는 대부분 IP 9개). **"극적 개선"이 나오지 않을 수 있다.** 그 경우 "소규모 데이터에서의 한계와 방법론"이 결과가 된다.
2. 군집이 비군집 방법과 비슷하게 나올 수 있다(2절 비판).

4. 데이터가 늘면 결과가 달라진다. 서버(교수님)나 친구 허니팟 데이터가 생기면 일반화 실험 후보가 된다.

## 8. 선행 연구 조사 (제한적 검색, 원문 미정독)

조사 에이전트가 웹 검색으로 수집했다. **전수 조사가 아니고 본문을 정독하지 않았다.** 표의 "확인"은 논문 페이지에서 제목·저자·게재처를 직접 본 것, "검색확인"은 검색 요약으로만 본 것이다. 인용하기 전에 원문을 직접 확인해야 한다.

| 주제 | 연구 | 수준 | 우리와의 관계 |
|---|---|---|---|
| Cowrie 군집화 | Boffa 등, *Towards NLP-based Processing of Honeypot Logs*, EuroS&PW 2022 | 검색확인 | 정규화·TF-IDF·군집화 구조가 가장 가깝다. 시그니처 결합·폐루프 없음 |
| 변종 발견 | Sanna Passino 등, *Nested Dirichlet models for unsupervised attack pattern detection in honeypot data*, Annals of Applied Statistics 2025 (arXiv:2301.02505) | 확인 | 군집(토픽)으로 변종을 찾았다는 직접 선행 사례. 규칙 환류는 없음 |
| IP 연결 | Crespi 등, arXiv:2104.10232 (2021) | 확인 | IP 단위, 우리는 행동 단위 |
| 소수 IP 편중 | Shamsi 등, *Measuring and Clustering Network Attackers using Medium-Interaction Honeypots*, WTMC 2022 (arXiv:2206.13614) | 확인 | 소수 IP가 연결의 큰 비중을 차지한다는 보고 |
| 허니팟→시그니처 | Nemean (Yegneswaran 등, USENIX Security 2005), Honeycomb, Autograph, Polygraph, Hamsa | 검색확인 | "허니팟 → 군집 → 시그니처 → 오탐 평가"의 원형. 대상이 네트워크 패킷 |
| 군집→규칙→검증 | Raff 등, *Automatic Yara Rule Generation Using Biclustering*, AISec 2020 (arXiv:2009.03779) | 검색확인 | 구조가 같고 대상이 악성코드 바이너리 |
| 군집 평가 | HDBSCAN (Campello 등, PAKDD 2013), DBCV (Moulavi 등, SDM 2014) | 검색확인 | 라벨 없는 내부 지표 |
| 평가 방법론 | Arp 등, *Dos and Don'ts of ML in Computer Security*, USENIX Security 2022 | 확인 | 데이터 누수·표본 편향 체크리스트로 쓴다 |
| 시간 분할 | TESSERACT (Pendlebury 등, USENIX Security 2019) | 검색확인 | 시간 분할 평가의 근거 |
| 중소기업 허니팟 | HoneyLite (PMC12390182, 2025 추정) | 검색확인 | 서지 일부 미확인 |

그 밖에 편집 거리로 Cowrie 세션을 묶은 연구(악성 세션의 대부분이 두 패턴이라는 보고), 석사논문, 실무 글이 나왔으나 서지를 확정하지 못했다. 우리 데이터의 "상위 2개 패턴 73%"와 같은 현상이라는 점이 눈에 띄지만 인용하려면 출처부터 확인해야 한다.

### 객관적 정리
- **차별성으로 주장하기 어려운 것**: "군집으로 허니팟 세션 패턴을 찾는다", "군집으로 변종을 찾는다", "허니팟에서 규칙을 자동 생성한다"는 이미 있다(패킷·악성코드 수준 포함). 우리 수치로 성능 우위를 주장할 수도 없다(기존 방법과 비교하지 않았다).
- **조건부로 주장 가능한 것**: (1) 셸 명령어 세션 수준에서 "같은 규칙 조합이 서로 다른 군집에 속하는 사례"를 규칙 개선 신호로 쓰는 교차 분석, (2) 후보 동결 → 시간 홀드아웃 → 승격의 사전 등록형 폐루프, (3) 규칙 해시·데이터 기록 추적. 이 세 가지는 이번 검색에서 같은 선행 연구를 **찾지 못했다**는 뜻이며 신규성이 입증된 것이 아니다. 라벨 없이 규칙 제거 실험으로 평가하는 조합도 찾지 못했다(미확인).
- **소규모 데이터의 한계**: 약 1개월, 고유 순서 133개라서 일반화 주장은 어렵고, 사례 연구와 방법론 제안 수준이 안전하다. 신뢰구간·반복 평가, 중복 제거 전후 결과를 함께 보고해야 한다.
- **투고 후보(요건·마감 미확인)**: EuroS&P Workshops(WTMC), ACSAC 워크숍, DIMVA·RAID의 단문·포스터·워크숍, Computers & Security 같은 저널. 단문·워크숍·경험 보고(experience report) 형태가 현실적이다.

## 9. 결정 사항과 남은 협의 (2026-11-28)

사용자가 결정한 것:
- 첫 후보는 군집 4(X04 세분화, **기존 시그니처 개선**)와 군집 5·7(BusyBox 탐침 규칙, **신규 행동 패턴 규칙화**)이다. 둘은 구분해서 평가한다. BusyBox 사용 자체를 악성으로 단정하지 않고 전후 행동과 맥락을 검증한다.
- 사람 판정은 사용자와 팀원이 한다. 100개 표본, 각자 60개(공통 20개 포함), Cohen's κ로 일치도를 낸다. 실제 판정 일정은 팀원과 협의한다.
- 비교군: 단순 시그니처, 고유 순서 그룹핑(필수), 편집 거리 기반(가능하면), ML 군집 교차 분석.
- `cluster.py` 이상 점수 문제는 `docs/handoff-cluster-outlier.ko.md`로 팀원에게 전달한다. ML 코드는 협의 전 수정하지 않는다.
- 이 분석 문서의 커밋을 승인했다. 문서 커밋과 구현 커밋은 분리한다.

남은 것: SDD 명세와 구현 계획(`docs/advancement-spec.ko.md`)의 승인, 팀원과의 판정 일정, ML 수정 협의.
